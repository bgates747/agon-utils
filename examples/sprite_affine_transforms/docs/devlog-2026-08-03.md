# Development log — 2026-08-03

Created a dedicated regression-fixture project in `agon-utils` for the sprite
affine-transform firmware work. The boundary keeps assembly programs, generated
RGBA2222 assets, expected results, reports, and mutable emulator state outside
the VDP source repository.

The emulator profile is bespoke and fail-closed. It uses the owned Fab build
and matching Console8 MOS, and names the future native module in the dedicated
VDP checkout. The module does not exist yet; this is an explicit setup gate,
not permission to run the stock VDP.

At initial setup, no emulator behavior had been human-validated. All changes
remain uncommitted and unpushed under the canonical emulator validation rule.

## First bespoke VDP build and launch

The dedicated VDP checkout was given the visible boot identity
`SpriteAffineDev` in `video/version.h`. A minimal external userspace adapter and
Makefile were added under that checkout's `userspace/`; generated objects and
the module remain under its ignored `video/build/userspace/` directory.

Build the module with:

```bash
make -C /home/smith/Agon/mystuff/agon-vdp-sprite-transforms/userspace \
  FAB_ROOT=/home/smith/Agon/mystuff/fab-agon-emulator
```

Then repair/verify and launch the profile with:

```bash
cd /home/smith/Agon/mystuff/agon-utils
.venv/bin/python \
  examples/sprite_affine_transforms/scripts/setup_emulator.py
cd examples/sprite_affine_transforms
./scripts/run_emulator.sh
```

The first successful launch used the module at
`video/build/userspace/vdp_sprite_affine_transforms.so`. `nm -D` showed all 15
symbols required by Fab's VDP ABI, and `ldd` reported no missing dependencies.
Fab's verbose output named that module by absolute path, initialized VDP mode
0, completed `wait_eZ80`, and continued through ordinary boot processing. The
screen identified the firmware as `Agon Platform VDP Version 2.16.0
SpriteAffineDev`. The Author visually confirmed this first launch as a good
test on 2026-08-03. The emulator was then shut down cleanly. The Author
subsequently approved committing the verified environment setup. No push was
requested.

### Hiccups and durable lessons

1. Upstream `agon-vdp` v2.16.0 does not contain a userspace adapter. The
   PingoWolf adapter is useful as a build reference but is subsystem-specific;
   this project needs its own minimal adapter and target name.
2. The first host build exposed four already-known portability gaps between
   release firmware and Fab's userspace shim: ESP-IDF-only
   `heap_caps_get_allocated_size`, mismatched `unsigned`/`size_t` YMODEM member
   definitions, a no-return userspace Intel HEX stub, and unqualified `max`.
   Narrow `#ifdef USERSPACE` or standard-C++ fixes were taken from the proven
   owned VDP tree; compiler return-type checking was not disabled.
3. The compatibility-layer build emits many pre-existing warnings and enough
   output to hide the actual error in a truncated terminal result. Capture a
   failed build log under `/tmp` and search specifically for `error:` before
   changing flags.
4. A project profile nested below its fixture project must not map the entire
   project as its SD directory. This profile maps only the ignored `build/`
   directory, preventing recursive filesystem traversal.
5. A broken module symlink is intentional before the first build. The launcher
   checks `-e` and fails before Fab starts, preventing fallback to stock VDP.
6. Rebuilds do not affect a running Fab process. Stop it and launch a fresh
   process after every module rebuild.

## First physical-hardware flash

The Author connected the target and explicitly authorized flashing. The
unreviewed assembly fixture delivered concurrently by another agent was not
read, built, staged, or deployed during this operation.

PlatformIO 6.1.19 built the committed VDP source at `e67f104` for
`esp32dev` using Espressif32 platform 6.6.0 and vdp-gl `ac2dd59`. The build
reported 44,688 bytes RAM (13.6%) and 1,077,173 bytes program flash (82.2%).
The generated `firmware.bin` was 1,077,552 bytes, contained the
`SpriteAffineDev` identity string, and had SHA-256:

```text
717a21a435d8bd24c2627fdca6934f1e5a8336d443124ea31fb3570bb3a4330d
```

The only detected USB serial target was the CH340 stable path:

```text
/dev/serial/by-id/usb-1a86_USB_Serial-if00-port0
```

PlatformIO/esptool identified an ESP32-PICO-D4 revision 1.1 with a 40 MHz
crystal. Upload ran explicitly through the stable path at 600000 baud. The
bootloader, partition table, boot-app image, and application image were
written; esptool verified the hash of every region and hard-reset the board via
RTS. This proves build, transport, write, and reset success. It does not by
itself prove the post-reset display, input, audio, or sprite behavior; those
remain human/hardware validation gates.

The Author subsequently confirmed that the physical machine booted with the
unique `SpriteAffineDev` signature and that AgonJukebox ran successfully.
That exercise covered the audio subsystem, one bitmap load, and an ordinary
non-sprite bitmap plot. The Author accepted this as sufficient evidence that
the trivial firmware identity change and userspace portability setup did not
break the standard functionality exercised by this smoke test. Sprite behavior
and affine sprite transforms were not exercised and remain separate validation
work. The Author approved committing this hardware-validation record.

## Accepted pre-change bitmap/sprite baseline

The generic assembly fixture supplied by the other agent was reviewed before
use. It keeps every VDU `u16` packet write byte-exact in ADL mode, uses an
explicit `dl` for its only 24-bit motion value, resets sprites before clearing
their bitmap buffers, and leaves the proposed but unsupported transform hook
uninvoked. `ez80asm` assembled all eight source files into a valid 1,802-byte
MOS executable with SHA-256:

```text
0e2ab3f47fbd6fdbafe4b8bf5495b5b9b7d0844cdbd1ddb4fbcc3fadc5a68340
```

Qualification found and corrected two integration defects:

1. The profile autoexec loaded the MOS executable but omitted `run`, so the
   emulator booted normally without entering the fixture. The generator now
   emits a CRLF `run` command and migrates only its exact former generated
   content, preserving any user-modified autoexec.
2. The animation loop loaded coordinates before `vdu_sprite_select`, whose
   documented clobber set includes `BC` and `DE`. Both sprites consequently
   moved to `(0,0)` after their correct initial placement. Selection now occurs
   before loading the coordinates.

After correction, a bounded headless run proved mode 8 selection, a 256-byte
upload to buffer `0x5100`, 16×16 RGBA2222 bitmap creation, an ordinary bitmap
plot, two-sprite activation, hardware selection for sprite 1, and coherent
motion beginning at `(9,144)` and `(169,144)`. A fresh interactive Wayland run
then passed the Author's visual test, including the baseline regular bitmap,
software sprite, hardware sprite, motion, and requested `S`/`H` backend
switching. The Author accepted this result as the pre-transform baseline and
approved committing it.
