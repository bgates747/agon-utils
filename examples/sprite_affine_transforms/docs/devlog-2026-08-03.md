### Hiccups and durable lessons

1. Upstream `agon-vdp` v2.16.0 does not contain a userspace adapter. The
   PingoWolf adapter is useful as a build reference but is subsystem-specific;
   this project needs its own minimal adapter and target name.
2. The first host build exposed four already-known portability gaps between
   release firmware and Fab's userspace shim: ESP-IDF-only
   `heap_caps_get_allocated_size`, mismatched `unsigned`/`size_t` YMODEM member
   definitions, a no-return userspace Intel HEX stub, and unqualified `max`.
   Narrow `#ifdef USERSPACE` or standard-C++ fixes were taken from the proven
   owned VDP tree; compiler return-type checking was not disabled.
3. The compatibility-layer build emits many pre-existing warnings and enough
   output to hide the actual error in a truncated terminal result. Capture a
   failed build log under `/tmp` and search specifically for `error:` before
   changing flags.
4. A project profile nested below its fixture project must not map the entire
   project as its SD directory. This profile maps only the ignored `build/`
   directory, preventing recursive filesystem traversal.
5. A broken module symlink is intentional before the first build. The launcher
   checks `-e` and fails before Fab starts, preventing fallback to stock VDP.
6. Rebuilds do not affect a running Fab process. Stop it and launch a fresh
   process after every module rebuild.

## Sprite-affine implementation

The experimental implementation now binds a matrix buffer to the selected
sprite through VDP variable `0x1412`, with selected-sprite state reported by
`0x1413` and the behavior gated by test flag 3. A valid nonsingular 2D affine
matrix is copied, validated, and inverse-sampled outside scanout into private
RGBA2222 frames. Both software sprites and hardware-requested sprites consume
the immutable cache; no floating-point sampling or mutable matrix state enters
the VGA scanline ISR. Translation, scaling, rotation, reflection, shear, and
nonsingular compositions work for every sprite-capable source format:
RGBA2222, RGBA8888, and Mask.

All animation frames are built as one transaction. Matrix and source-bitmap
generations invalidate the cache, while a rejected matrix generation retains
the complete last-good result only if all source identities still match.
Mask, unsupported logical paint modes, and RGBA8888 XOR use the software path;
eligible Set and RGBA2222 XOR sprites can remain hardware-composited. The
original bitmap buffers are never rewritten.

The parser was also hardened so every gated affine command consumes its full
payload while disabled. Matrix-set headers and values, inline and buffered
operands, bitmap/data-transform option tails, dimensions, byte counts, spans,
and offset arithmetic are checked before use. Unknown reserved matrix
operations are rejected rather than partly interpreted.

## Publication and object-lifetime audit

The paired renderer now exposes checked bitmap and sprite-list admission,
coherent pointer/count/stride publication, and an explicit retirement fence.
The firmware publishes an immutable proxy list, detaches it before destructive
changes, crosses the renderer fence, and only then frees old frame storage.
The ESP32 fence waits across scanout; the userspace renderer serializes with
framebuffer readers. A deterministic native publication/lifetime regression
passed ten consecutive runs.

Failure-path review found and corrected several broader bitmap lifetime bugs
while exercising same-ID replacement:

1. Bitmap replacement now preallocates map/vector/metadata state, retires the
   old object, and only then commits the replacement and its generation.
2. Ordinary queued Canvas plots are completed before clearing a bitmap or its
   backing buffer, closing a pre-existing use-after-free window.
3. Screen capture is completed before the new bitmap is published to plots or
   sprites.
4. Bitmap-user retirement no longer allocates while handling low-memory
   destruction.
5. Replacing an active custom mouse cursor now hides it and crosses the same
   renderer retirement fence before releasing its frames.

Two portable torture phases were added for the queue/replacement and immediate
screen-capture-consumer cases. They supplement the native deterministic test;
they are visual/liveness checks rather than allocator instrumentation.

## Physical mode-admission regression and correction

The first full sprite-affine ESP32 artifact reported 73,496 bytes of RAM. It
booted with the custom signature and ran AgonJukebox, but the Author observed
that Jukebox's request for mode 20 (512x384x64, single buffered) remained on a
640x480 display. Inspection identified 28,672 bytes of unconditional new BSS:
8,192 bytes for renderer proxies, 18,432 bytes for transform states, and 2,048
bytes for retired-frame ownership. That consumed the framebuffer headroom and
made mode-20 allocation fall back to mode 0.

The implementation was changed so transform state is allocated lazily per
bound sprite in preferred PSRAM. The renderer proxy is now a checked,
exact-high-water allocation in explicitly internal-capable RAM; plain `malloc`
was rejected because this ESP32 configuration can route sufficiently large
allocations to PSRAM, which is not scanout-safe. The remaining fixed transform
index costs 1,024 bytes. Final reported static RAM is 45,840 bytes, only 1,152
bytes above the 44,688-byte upstream baseline. Normal `VDU 22` mode changes
deactivate sprites and release their proxy before framebuffer admission.

The corrected paired build used 45,840 bytes RAM and 1,098,025 bytes flash.
Its exact artifact is:

```text
/home/smith/Agon/mystuff/agon-utils/examples/sprite_affine_transforms/build/platformio-89fc37bb0ec132aa/build/esp32dev/firmware.bin
size:   1098400 bytes
sha256: db603aabeadad68f1529c83e3691034391aa94ef334e191bb69bf43bf736bebe
```

Esptool wrote and hash-verified that artifact on the connected ESP32-PICO-D4
and hard-reset the board. The Author confirmed the unique firmware signature,
AgonJukebox audio and ordinary bitmap operation, and successful mode-20 entry
after restarting the machine. This closes the standard-functionality and
framebuffer-admission smoke test for the final layout. No affine assembly
fixture has been installed on physical storage, so actual transformed-sprite
behavior remains emulator-validated rather than hardware-validated.

The lazy layout has a deliberate residual tradeoff: activating `N` sprites
needs approximately `32 * N` additional checked internal bytes for the proxy,
so the maximum active-sprite count may be lower in the tightest modes. A
failure to allocate the first small transform-state object currently reads as
unbound rather than resource-limited. These limitations and the mandatory
paired-renderer dependency are recorded in the design report.
