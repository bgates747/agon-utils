# Development Log — 2026-07-22

## Agon API review for the `.agnb` loader

Reviewed the official local Agon MOS, buffered-command, bitmap, enhanced-audio,
and VDU documentation against the focused slideshow-derived assembly harness
under `examples/agnb`. The resulting implementation précis is in
`docs/agnb-loader-agon-api-precis.md`.

The harness is intentionally broader than the minimum application and serves
as a test bed. The loader design should reuse relevant routines without
assuming every general-purpose helper belongs in the final path.

Principal findings:

- The loose-file baseline already uses the preferred modern pattern:
  `mos_fopen`, repeated 8 KiB `mos_fread` calls, and `mos_fclose`.
- In this slideshow harness, `filedata` is a deliberate fixed 8 KiB scratch
  window at `$B7E000`.
- Each read is appended as a VDP command-0 block; `vdu_load_img` then
  consolidates, selects, and creates the bitmap.
- The `.agnb` conversion should preserve that proven streaming machinery while
  moving the open/close boundary around the whole container and deriving buffer
  ID, image metadata, and exact transfer bounds from `BHDR`, `IMAG`, and `DATA`.
- The adopted `IMAG` order—width, height, format—matches the VDP
  bitmap-create payload exactly, and `BHDR` already matches the VDP's 16-bit
  buffer-ID byte order.
- A VDP block has a 65,535-byte maximum; buffers may contain multiple blocks.
  Bitmap data must be consolidated before bitmap creation, whereas future audio
  sample data may remain split across blocks.
- The generated loose-file table uses 15 bytes per image and its `MLT DE`
  indexing cannot uniquely address all 408 records. Container loading removes
  that table from the load path because every record contains its
  writer-specified buffer ID.

The recommended first vertical slice is a two-image `.agnb` container using
the existing MOS read loop and VDP helpers. After it renders on hardware, scale
to the 408-image benchmark before adding unknown-form seeking or audio.

The reusable loader itself must not hard-code the harness's `$B7E000` scratch
address or its 8 KiB size. It should operate on an application-provided 24-bit
pointer and capacity. Wolf3D already uses that onboard SRAM for map definitions
and may later load additional assets just in time, so it will choose a scratch
region suited to its own memory layout.

File-read size and VDP-upload size are separate. In ADL mode `mos_fread` accepts
a 24-bit count, whereas `RST 18h` and one VDP command-0 block use 16-bit lengths.
When a complete RIFF payload fits in the caller's scratch region, the loader may
read it with one MOS call and then subdivide it for VDP upload. Otherwise it
uses the same scratch region as a moving window over the payload.

A standalone application may place an uninitialized scratch label immediately
after its program and calculate capacity up to an application-chosen ceiling.
The conventional moslet boundary is not enforced by memory protection; whether
scratch may enter that region is a caller compatibility decision. The loader
must neither assume nor enforce that policy.

## Documentation discrepancy checklist

Cross-checked the format specification, Agon API precis, and image-load-flow
note on 2026-07-22. Work through these in order so implementation guidance does
not silently become a second specification:

- [x] **1. Make buffer ID `0xFFFF` invalid in the format specification.** The
  API precis correctly identifies `0xFFFF` as a VDP-reserved buffer ID and
  requires the loader to reject it. Resolved by defining the loader-side rule
  in the normative `BHDR` and reader requirements: reject the record before
  issuing any VDP command for it. This remains an implementation reminder for
  the loader rather than a new runtime buffer-allocation mechanism.
- [x] **2. Label the first vertical-slice loader as deliberately
  non-conforming or include required skip behavior.** The specification
  requires readers to skip unknown optional chunks safely and permits skipping
  unsupported record forms by their enclosing `LIST` size. Resolved by
  labeling the exact-structure first slice a restricted prototype and making
  its early-validation boundary explicit across the specification, API precis,
  and load-flow note: read and validate `BHDR`, `IMAG`, the `DATA` header and
  declared size, and all enclosing bounds before reading payload bytes or
  issuing any VDP command. Unknown-chunk and unsupported-form skipping remains
  required before calling the loader fully conforming; read-and-discard is an
  acceptable implementation and does not depend on MOS 3 seeking.
- [x] **3. Keep the proposed audio descriptor clearly non-normative.** The
  specification says `AUDI` is undefined, writers must not emit it, and readers
  must treat it as unsupported. Resolved by recording the production
  AgonJuekbox application specification as the existing implementation
  precedent while making clear that those conventions are not yet the generic
  `.agnb` contract. The applicable fields, validation, and loader behavior will
  be formalized in a later container-specification revision.
- [x] **4. Reconcile unconditional consolidation with the block strategy.**
  Resolved by adopting the known-working strategy as the loader design: every
  bounded read becomes one VDP block and every successfully uploaded image is
  consolidated before bitmap creation. The loader will not add a separate
  single-block path. One universal path handles images on either side of the
  65,535-byte block limit, avoids size-dependent branching, and keeps the
  assembly implementation smaller.
- [x] **5. Correct the phrase “five reordered `IMAG` bytes.”** Resolved while
  documenting the early-validation flow: the note now says to retain the five
  `IMAG` bytes. Their adopted `width`, `height`, `format` order permits direct
  transmission without reordering.
- [x] **6. State the supported image-format scope consistently.** Resolved by
  making version 0.1 and the initial loader RGBA2222-only. Writers emit format
  1, and readers reject another format before reading or uploading its `DATA`.
  Other formats are deferred and may never be needed. If added, they should
  reuse the same raw-byte transport and bitmap-finalization path; only layout
  and payload-size validation differ. RGBA8888 needs a four-byte-per-pixel
  factor, while mono/mask rows require whole-byte rounding.

- [x] **7. Keep buffer-ID ownership with the writer.** Resolved by removing the
  proposed sequential-ID display optimization from the design guidance. Every
  record must contain the ID selected by the writer. The reader validates and
  uses that exact value; it does not allocate, derive, auto-increment, or remap
  buffer IDs. Record order does not determine destination IDs.

## Parallel harness layout

Moved the complete known-working loose-file benchmark under `loose/`, including
its assets, scripts, assembly source, generated targets, and emulator setup.
The generic project documentation remains at the project root. Created an
empty parallel `container/` skeleton with `scripts/`, `src/asm/`,
`tests/fixtures/`, and `tgt/`; implementation files will be added only as each
piece is developed. The loose image scripts received only the relative-path
adjustment required to continue finding the shared slideshow palette after the
move.

Aligned deployment paths with the parallel layout. The loose harness now copies
to `mystuff/agon-utils/examples/agnb/loose/tgt` on both its local emulator SD
card and physical media; its autoexec uses the same path. Added a matching
container emulator scaffold whose autoexec targets
`mystuff/agon-utils/examples/agnb/container/tgt`. Both variants have a tracked
shared `shared/scripts/setup_emulator.py` helper that accepts the target
emulator directory, recreates the shared emulator symlinks, and writes the
correct variant-specific autoexec on a fresh checkout. For example, pass
`loose/.emulator` or `container/.emulator`.

Moved the original and processed image sets to `shared/assets/` because both
harnesses consume them. Split the former combined image scripts by ownership:
`shared/scripts/prepare_images.py` now performs only original-to-processed PNG
preparation. It preserves original dimensions by default; `--scaled` explicitly
selects the cropped 320x240 mode. It also creates the headerless RGBA2222 file
paired with each processed PNG. `loose/scripts/do_assembly.py` reads shared PNG
dimensions and RGBA2222 sizes to generate `images.inc` as part of its `-a`
step, but does not perform image conversion. Its `-c` and `-sd` steps deploy
the shared `.rgba2` files under the loose target's `images/` directory. The
existing individual-step command-line switches remain available.

## First container-writer step

Created `container/scripts/do_assembly.py` incrementally rather than copying
the loose harness script. Its first implemented step scans the 408 shared
processed PNG/RGBA2222 pairs, validates dimensions and exact payload sizes,
assigns explicit buffer IDs beginning at 256, and writes
`container/tgt/images.agnb`. The resulting container is 1,739,624 bytes and
contains `VERS` followed by 408 aligned `LIST BUFR` image records.

The writer currently accepts `-b`/`--build-container`; with no other steps yet,
invoking it without options performs the same build. No assembly, deployment,
or emulator-launch behavior has been added to the container script.

Added an independent byte-level test under `container/tests/` that walks the
generated RIFF structures without using the writer's chunk helpers. It verifies
the RIFF size, zero padding, chunk and record ordering, version, explicit IDs,
image metadata, DATA sizes, all 408 source dimensions, and byte-for-byte DATA
equality with every shared `.rgba2` file. The test passes.

Added `container/scripts/view_agnb.py` as an independent interactive inspection
tool. It indexes the container, displays record metadata, extracts the selected
DATA payload to a managed temporary file, and uses the native
`agonutils.rgba2_to_img` conversion to produce the Pillow image. The Tk viewer
supports record stepping and direct jumps, integer 1x-32x nearest-neighbor zoom,
scrolling, and exact source-pixel byte/RGBA inspection under the cursor. The
headless parser/conversion check passed for all 408 indexed records, and the GUI
launched without startup errors. The UI was then adjusted for accessibility
with approximately doubled bold widget fonts, larger padding, and a larger
initial window while retaining exact nearest-neighbor image scaling. The user
visually inspected the running application and confirmed the viewer works well.

This establishes the first container milestone: a complete 408-image `.agnb`
artifact can be generated, independently validated at the byte level, decoded
through the native Agon image utilities, and inspected interactively record by
record. Assembly reader work has not started.
