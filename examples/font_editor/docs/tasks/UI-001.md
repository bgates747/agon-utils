# UI-001 — Resolve tiny widgets under Pop!_OS desktop scaling

Status: **Accepted — option 2 is the current solution.**
Created: 2026-09-10.
Accepted: 2026-09-10; removed from the unfinished-work index.

## Problem and evidence

The author reports that the editor's widgets appear very small despite the
desktop's scaling settings. The cause has not been confirmed.

Read-only inspection found a COSMIC Wayland session with an X display available.
`xrdb -query` showed cursor settings but no `Xft.dpi` resource. The editor's
startup did not explicitly configure Tk scaling. This suggested a possible
desktop-to-Tk scaling mismatch, but does not establish the cause. The installed
Tk version, DPI, and desktop scale had not yet been measured at that point;
the subsequent measurements and trials are in the development log.

The main entry point is `src/python/font_editor.py`. The UI mixes Tk and ttk
widgets and uses fixed pixel padding. `src/python/image_display.py` implements
separate font-atlas zoom. Application preferences are stored in XML.

## Options for review

1. [x] **Try COSMIC's X11 application scaling setting.** In Settings → Displays →
   X11 Window System Application Scaling, try **Optimize for applications** and
   restart the editor. Verify the setting's availability on the installed
   COSMIC version. Record the prior setting and the observed result. This is
   a desktop-wide adjustment that may affect other X11 applications.
   Trial launched on 2026-09-10; the installed version locates this control in
   Applications → Legacy Applications. Completion records execution of the
   trial, not acceptance of the visual result. The author rejected this approach;
   the trial desktop override has been removed. See the
   [trial evidence](../development/2026-09-10.md).

2. [x] **Add a persistent application UI-scale preference.** Provide Auto and
   explicit percentages such as 100%, 150%, and 200%, saved in the application's
   XML configuration. Apply Tk scaling before constructing widgets and account
   for fixed pixel padding, control dimensions, and any explicit font sizes.
   Keep font-atlas zoom independent of UI scaling and preserve exported font
   dimensions and bytes. Define percentage semantics clearly: Tk's raw scaling
   value is pixels per point, not a desktop percentage. Decide during design
   whether changes require restarting the app; Tk does not guarantee that
   existing widgets resize correctly after a scaling change.
   Implemented, launched at 200%, and accepted by the author on 2026-09-10.

3. **Improve automatic scale detection — deferred.** Retained as
   [UI-002](UI-002.md) for possible reconsideration at the author's request.

The author rejected option 1 and accepted option 2 after visual review. The
prior desktop configuration is restored. Auto uses Tk's existing startup
detection; enhanced detection is deferred in UI-002.

## Acceptance criteria for the selected approach

1. [x] The author verifies that controls and text are comfortably readable at the
   intended desktop/UI scale, including menus and relevant dialogs, with no
   clipping or inaccessible controls.
   The author reported "works" and accepted the current solution. The known
   color-picker validation limitation below remains recorded.
2. [x] Font-atlas zoom and ordinary `.font` exported content retain their intended behavior.
   Automated checks pass for atlas pixels, dimensions, glyph selection, and
   ordinary `.font` output at 100–250%. RGBA2 export remains blocked by an
   existing native API mismatch; see the development log.
3. [x] If an application preference is implemented, it persists across launches
   and has documented default, override, and restart behavior.
   Verified saving 150% during a 200% session, then applying it in a fresh process.
4. **Not applicable to the accepted solution:** improved automatic detection
   was deferred to UI-002, including its mixed-monitor and double-scaling checks.
5. [x] Verification uses the repository `.venv` and the prerequisite native-extension
   check required by the repository handoff before Python work. Record the
   actual environment and visual results when implementation is undertaken.
   The prerequisite check passed and the app was launched with the repository
   interpreter; see the trial evidence. The author subsequently accepted the UI.
